# willitharness: domain contract (v0.5)

Single source of truth for the BDD plan, the TLA+ specs and the Lean proofs.
Every property has an ID. Features, specs and theorems must cite these IDs.
Do not edit this file from a fork. Report problems in your own `contract-issues.md`.

Status: DRAFT for the spike. Language default: Python (proposed, not final).
CLI and package name: `willitharness`.
Version history: v0.1 is kept as `contract-v0.1.md`. Section 11 lists every change
from v0.1 to v0.4, and the finding that caused each.

## 1. Purpose
Check whether the rules you write for a coding agent work. For each rule, answer
four questions and give a decision: fix the loading, keep, replace with a script,
or delete candidate.

## 2. Glossary
- Harness: the files that shape an agent (CLAUDE.md, AGENTS.md, skills, hooks).
- Rule: one instruction in a harness file that targets one observable behavior.
- Detector: the check that decides whether a run broke the rule. Kind `forbidden`:
  the run broke the rule when a command or tool call matches any of its actions. An
  action is command words, then options: `pgrep -f` matches program `pgrep` with the
  short flag `f` in any cluster (`-f`, `-fl`, `-lf`), case-sensitive; `--full` is
  its own action. Plain `pgrep vitest` does not match `pgrep -f`. Kind `required`: the
  run broke the rule when a named action is absent before a named point, such as
  the first edit or the final answer. See R1.
- Channel: how the rule text reaches the agent's context: `file` (CLAUDE.md or
  AGENTS.md), `skill`, `hook` (text added by a hook) or `system_prompt`. An arm
  records one channel. The default is `file`.
- Arm: one variant of the harness, built as an overlay directory and a label.
- Rule arm: the harness with the target rule loaded.
- Leave-one-out arm (LOO): the harness with exactly the target rule removed. It
  still loads every other rule.
- Noise arm: a second run of the LOO arm with an identical configuration. The pair
  (LOO, LOO repeat) is the noise pair.
- Guard: a script that blocks a command and returns a block message.
- World: the stubs and fixtures a run uses. A bad world invalidates runs.
- Task: a prompt, a fixture and deterministic checks.
- Run: one agent session on one task in one arm.
- Outcome: a binary property of a run. v0 defines three: `attempted_violation`,
  `completed`, `blocked_count` (count, reported only).
- Usable run (per outcome): see section 4.
- Cell: one (arm, task) pair. Reps: usable runs wanted per cell.
- Plan: arms, tasks, reps and a budget.
- Budget: the spend cap in USD. RUN_CAP is the per-run cap. Assumption A-CAP: the
  runner enforces RUN_CAP (for example with a wall-clock limit), so one run never
  costs more than RUN_CAP. A run that would exceed it is ended and recorded
  unusable.

- Resume: the transition from BudgetStopped back to Running with a higher budget.
  See section 7.
- Fingerprint: a hash of the plan with `budget_usd` left out. The implementation
  stores it at the first run and compares it at resume (A-FP, section 7).

Constants: MIN_RUNS = 5. DEFAULT_REPS = 20. MAX_RETRIES = 2. MIN_PROBE_RUNS = 3.
z = 1.96.

## 3. The four questions
- Q1 Reachability: is the rule text in the agent's context, in the real directory?
  Result: Loaded, Masked or Unknown. Rules P1 to P4 in section 5.
- Q2 Effect: does the rule change the target behavior? LOO arm against rule arm,
  with the noise pair. Result: EffectResult, mapped by E1.
- Q3 Guard: would a script do as well? Result: GuardResult, defined by G1.
- Q4 Side effects: what else changed? Report only (S1, S2).

## 4. Verdict function (exact)
Inputs: (k1, n1) and (k2, n2) for one outcome in one task. n counts runs usable for
that outcome. k counts those with the outcome true.
Verdicts are computed per task cell first. A pooled verdict across tasks is allowed
only if it is labeled `pooled` and carries a warning (task clustering is ignored).
Interval: Wilson for (k, n). Difference interval: Newcombe hybrid over the two
Wilson intervals, as a pair (lo, hi).
Assumptions on the difference interval (stated, because the proofs need them):
- DI-1 ordered: lo <= hi.
- DI-2 swap: diffInterval(b, a) = (-hi, -lo) where (lo, hi) = diffInterval(a, b).
Verdict values: InconclusiveSmallN, FirstHigher, FirstLower, Inconclusive.
Rule:
1. if min(n1, n2) < MIN_RUNS then InconclusiveSmallN
2. else with (lo, hi) = diffInterval((k1, n1), (k2, n2)):
   lo > 0 gives FirstHigher; hi < 0 gives FirstLower; otherwise Inconclusive.

Usable run, per outcome:
- For `attempted_violation`: the run ended with a result and no harness error.
- For `completed`: as above, and no permission denial of a command the task needs.
- Unusable runs never count in n or k. The report counts denials per cell and warns
  (W-DENIAL) when every run in a cell has one.

Properties:
- V1 Totality and exclusivity: exactly one verdict value for any valid input.
- V2 Small-n rule: if min(n1, n2) < MIN_RUNS the verdict is InconclusiveSmallN,
  whatever k1 and k2 are.
- V3 Swap symmetry (given DI-1 and DI-2): verdict(a, b) = flip(verdict(b, a)).
  flip swaps FirstHigher and FirstLower and fixes the other two values.
- V4 Identical counts: verdict((k, n), (k, n)) is never FirstHigher or FirstLower.
- V5 Interval bounds: 0 <= low <= k/n <= high <= 1 for 0 <= k <= n, n >= 1.
  Property-tested, not proven. Lean assumes it.
- V6 Noise validity. NoiseStatus has three values:
  - NoiseUnmeasured: the noise pair has fewer than MIN_RUNS usable runs on a side.
  - NoiseFloorTooHigh: the noise pair verdict is FirstHigher or FirstLower.
  - NoiseOk: otherwise (the noise pair verdict is Inconclusive).
  No effect verdict is emitted unless NoiseStatus = NoiseOk. A plan with no noise pair
  has NoiseStatus = NoiseUnmeasured. The report computes NoiseStatus per outcome and
  shows the `completed` NoiseStatus as a line. E1 uses `attempted_violation`, and G1
  is unchanged by the `completed` line.
Warnings (report only, never change a verdict): W-LOWN below DEFAULT_REPS usable
runs in a cell; W-DENIAL as above; `saturated` when the LOO arm has k = 0 for the
target outcome (the model may already obey the rule); `AtBound` when both arms of a
comparison have k = 0, or both have k = n: an Inconclusive verdict then carries the
reason "both arms at 0% (or 100%); harder tasks are needed"; `pooled` as above.

## 5. Rules for Q1, Q3, Q4, world and effect

### Q1 probe rules
Inputs satisfy 0 <= targetHits <= runs and 0 <= controlHits <= runs. Only usable probe
runs count toward runs.
A probe run asks the model for a token. Each arm has a target token (present only in
the rule arm) and a control token (present nowhere).
- P1 Refuse a probe with fewer than MIN_PROBE_RUNS runs per arm: result Unknown.
- P2 If the control token appears in any probe run, the probe is invalid: Unknown.
- P3 Otherwise the target token in every run gives Loaded, in no run gives Masked,
  in some runs but not all gives Unknown.
- P4 The LOO arm is probed with a non-target token that is present in the harness
  and must be Loaded. P1 and P2 apply to this probe too. If it is not Loaded, the LOO
  arm is invalid, the EffectResult is Invalid and the plan cannot report an effect.
  Rule L7 applies to the rule arm only, because P4 covers the LOO arm.

### R detectors
- R1 A `required` detector decides a run only from a complete transcript: one that
  ends with a result event and no harness error. A run cut off before the named
  point is unusable for the outcome.

### E1 effect mapping
The effect verdict compares the LOO arm (first) with the rule arm (second) on
`attempted_violation`.
| NoiseStatus | verdict(LOO, rule) | EffectResult |
|---|---|---|
| not NoiseOk | any | Invalid |
| NoiseOk | InconclusiveSmallN | NotEnoughRuns |
| NoiseOk | FirstHigher | RuleLowersViolations |
| NoiseOk | FirstLower | RuleRaisesViolations |
| NoiseOk | Inconclusive | NoMeasurableEffect |
NoMeasurableEffect means "not measurable at this n". It does not mean "no effect".

### G1 guard result
Inputs: the `completed` verdict of (guard-only arm, rule arm), coverage in {Full,
Partial, NoneSeen}, and bypass in {Zero, Some}.
- Coverage is Full when the guard blocked every violating command it saw and saw at
  least one. It is Partial when it let one pass. It is NoneSeen when it saw no
  violating command in any guard-arm run.
- bypassRate is the guard-arm usable runs with a bypass divided by the guard-arm
  usable runs. Bypass is Zero iff bypassRate = 0.
- Bypass: the effect came through a channel the block message did not offer. A
  non-Bash tool such as Write or Edit that writes the blocked command's target path
  is a bypass. A command the block message offered is not a bypass. An absolute-path
  call of the same program is an alternative channel: reported, not counted.
- GuardUntested iff no guard arm was run, or the completed verdict is
  InconclusiveSmallN, or coverage = NoneSeen. No evidence is not "worse".
- GuardMatchesRule iff not GuardUntested and the completed verdict is not
  FirstLower and coverage = Full and bypass = Zero.
- GuardWorse: any other case.

### S side effects
- S1 The report lists commands whose use differs between arms, with counts per arm.
- S2 The side-effect report never changes a decision.

### W world validation
- W1 Every command a task names has a stub or is declared real.
- W2 Stub output references only paths inside the world.
- W3 A world hash is stored at validation. If the hash changes, the world is no
  longer validated.
- W4 Every task has a prompt file `prompts/<task>.txt` in the world, with text. The
  world hash covers it.
- W5 A prompt holds none of these words, matched whole and without regard to case:
  benchmark, evaluation, grader, rubric, score, detector, verdict, noise,
  leave-one-out.

Run environment (a statement, not an ID). Effect runs have the Bash tool only. Guard
runs (a plan with a `guard_only` arm) have Bash, Write and Edit, so a bypass can be
seen. Probe runs have no tool. A Bash allowlist is built from the commands named in
`tasks.txt` and `real.txt`, with permission mode `default`, so a denied attempt stays a
countable permission denial. Each stub is a runnable wrapper that the runner generates
from the stub data in the workspace `bin/` folder, first on PATH: it logs its arguments
to `calls.log`, prints the stub output and exits 0. `world check` runs nothing from the
world.

## 6. Decision table (exact)
Decision values: FixLoading, Keep, ReplaceWithGuard, DeleteCandidate,
NeedsMoreRuns, CannotDecide.
Inputs: reach in {Loaded, Masked, Unknown}; effect in {RuleLowersViolations,
NoMeasurableEffect, RuleRaisesViolations, NotEnoughRuns, Invalid};
guard in {GuardMatchesRule, GuardWorse, GuardUntested}.
- D1 reach = Masked gives FixLoading (any effect, any guard).
- D2 reach = Unknown gives CannotDecide.
- D3 reach = Loaded and effect = Invalid gives CannotDecide.
- D4 reach = Loaded and effect = NotEnoughRuns gives NeedsMoreRuns.
- D5 reach = Loaded and effect = RuleRaisesViolations gives DeleteCandidate.
- D6 reach = Loaded and effect = NoMeasurableEffect gives DeleteCandidate. The report
  text for D6 says "not measurable at this n" and shows the `saturated` flag.
- D7 reach = Loaded and effect = RuleLowersViolations and guard = GuardMatchesRule
  gives ReplaceWithGuard.
- D8 reach = Loaded and effect = RuleLowersViolations and guard in
  {GuardWorse, GuardUntested} gives Keep.
Derived properties:
- D9 Totality and determinism: the table is a total function on all 45 inputs.
- D10 ReplaceWithGuard only when guard = GuardMatchesRule and
  effect = RuleLowersViolations and reach = Loaded.
- D11 DeleteCandidate is never returned when effect = RuleLowersViolations.
- D12 Masked rules are never reported as Keep, ReplaceWithGuard or DeleteCandidate.

## 7. Run lifecycle (state machine)
Plan states: Drafted, WorldValidated, ReachabilityChecked, Running, Complete,
BudgetStopped, Aborted, Analyzed, Reported.
Order: Drafted, WorldValidated, ReachabilityChecked, Running, then Complete or
BudgetStopped, then Analyzed, then Reported. A world hash change (W3) moves the plan out of WorldValidated and
stops new runs from starting until it is validated again. From WorldValidated or
ReachabilityChecked the plan goes back to Drafted. In Running it stays Running with
starts blocked. Reachability results are kept. Assumption: the world changes finitely
often.
Resume: the transition BudgetStopped to Running. It has these rules:
- It starts only from BudgetStopped. A Complete plan never resumes.
- It needs a `budget_usd` strictly higher than the current one. A budget never goes
  down (L11).
- It needs a validated world: the world hash is unchanged since validation (W3). If the
  world changed while the plan was BudgetStopped, validate the world again first.
- Reachability results are kept.
- It resets `endedBy`, so a Running plan is never marked as ended (L12).
- Assumption A-FP: the plan is identical except `budget_usd`. The implementation
  enforces it with a fingerprint of the plan with `budget_usd` left out. The TLA+ model
  does not check A-FP. It has no plan content.
- Analyzed is final. `analyze` on a BudgetStopped plan moves it to Analyzed, and then
  Resume is not possible. The `analyze` command prints a warning that it ends resume.
- Run records carry no world hash. The runner cannot show which world made an older
  run. This is a known gap. A separate task closes it (backlog T62).
Abort is reachable from any state before Analyzed. An Analyzed or Reported plan is
final and cannot be aborted.
Run states: Started, RecordedUsable, RecordedUnusable. "Pending" is derived: a cell
has pending work when usable runs plus runs in flight are fewer than `reps` and attempts
are below reps + MAX_RETRIES. It is not stored.
Transitions: a Started run ends as RecordedUsable, or RecordedUnusable (harness
failure, timeout, or cost above RUN_CAP). A timeout charges the full RUN_CAP and counts
as an attempt. Abort records every in-flight run as
RecordedUnusable and charges RUN_CAP for it.
Retry: an unusable run does not use up a rep. The runner may start another run in
the cell while attempts are below reps + MAX_RETRIES. When every retry is used and a
cell still has fewer than `reps` usable runs, the plan still ends Complete, and the
small count gives NotEnoughRuns. BudgetStopped happens only when the budget blocks a
start.
Safety:
- L1 No run is Started before the plan is Running. Running needs the world
  validated and a reachability result (Loaded, Masked or Unknown) for every arm of
  the plan.
- L2 Budget: let reserved = RUN_CAP times the number of Started, unrecorded runs. A
  run is Started only if spent + reserved + RUN_CAP <= BUDGET. A record replaces
  the reservation with the real cost. So spent <= BUDGET always (under A-CAP).
- L3 Immutability: a recorded run never changes. The model checks that counters
  never decrease. Per-run immutability is tested in the implementation.
- L4 Usable runs per cell never exceed `reps`.
- L5 No verdict before the plan is Complete or BudgetStopped. An Aborted plan gets
  no verdict.
- L6 Counts use runs usable for the outcome only.
- L7 An arm with reach = Unknown gets no effect verdict.
- L8 An effect result is Reported only if the plan has a noise pair and
  NoiseStatus = NoiseOk.
- L9 Attempts per cell never exceed reps + MAX_RETRIES.
- L10 Resume legality: a Resume step happens only from BudgetStopped, with the world
  validated, with a strictly higher budget, and it ends in Running with `endedBy`
  reset.
- L11 The budget never decreases.
- L12 A Running plan is never marked as ended.
Liveness. Assumption F: the runner steps are weakly fair. Abort and timeout are not
assumed fair.
- T1 Every Started run is eventually recorded (usable or unusable).
- T2 If the plan is never aborted, every Running plan eventually reaches Complete
  or BudgetStopped.
- T2a If abort is allowed, every Running plan eventually reaches Complete,
  BudgetStopped or Aborted.

## 9. Out of formal scope (be honest in every document)
- Agent behavior (LLM output) is not formalized. It is measured.
- Shell command parsing for violation checks is covered by property tests and a
  corpus of good and bad commands, not by proofs.
- The numeric Wilson and Newcombe implementation is covered by property tests and
  known-value tests. Lean treats the interval endpoints as an oracle with DI-1,
  DI-2 and V5.
- The `claude` CLI, hooks and permission behavior are observed, not proven.
- TLA+ models are bounded and use smaller constants than the product (for example
  MIN_RUNS 1 or 2). Passing a bounded run is not a proof for all sizes. The
  lifecycle logic does not depend on the exact constants.
- A-CAP (RUN_CAP is a true cap) is an assumption about the runner, not proven.
- A-FP (the plan is identical except `budget_usd` at resume) is enforced by the
  implementation fingerprint. TLA+ does not check it.

## 10. Checkpoint rule
A milestone is done only when its executable gates pass: tests green, checks
proven able to fail (a bad example each check must reject), the TLC runs agree
with their expected verdicts, the Lean project builds with no `sorry`, and the
spend stays under the stated cap.
