# willitharness: domain contract (v0)

Single source of truth for the BDD plan, the TLA+ specs and the Lean proofs.
Every property has an ID. Features, specs and theorems must cite these IDs.
Do not edit this file from a fork. Report problems in your own `contract-issues.md`.

Status: DRAFT for the spike. Language default: Python (proposed, not final).
CLI and package name: `willitharness`.

## 1. Purpose
Check whether the rules you write for a coding agent work. For each rule, answer
four questions and give a decision: fix the loading, keep, replace with a script,
or delete candidate.

## 2. Glossary
- Harness: the files that shape an agent (CLAUDE.md, AGENTS.md, skills, hooks).
- Rule: one instruction in a harness file that targets one observable behavior.
- Arm: one variant of the harness, built as an overlay directory and a label.
- Noise arm (A/A): a second run of an identical arm. It measures run-to-run noise.
- Leave-one-out arm: the harness with exactly the target rule removed.
- Guard: a script that blocks a command and returns a block message.
- World: the stubs and fixtures a run uses. A bad world invalidates runs.
- Task: a prompt, a fixture and deterministic checks.
- Run: one agent session on one task in one arm. It ends usable or unusable.
- Usable run: ended with a result and no harness error. Unusable runs never count.
- Cell: one (arm, task) pair. Reps: runs planned per cell.
- Plan: arms, tasks, reps and a budget.
- Budget: the spend cap in USD for a plan. RUN_CAP is the per-run cap.

## 3. The four questions
- Q1 Reachability: is the rule text in the agent's context, in the real directory?
  Result: Loaded, Masked or Unknown.
- Q2 Effect: does the rule change the target behavior? Rule arm against
  leave-one-out arm, with a noise arm. Result: see EffectResult.
- Q3 Guard: would a script do as well? Guard-only arm against rule arm on
  completion. Result: GuardMatchesRule, GuardWorse or GuardUntested.
- Q4 Side effects: what else changed (other commands, turns, cost)? Report only.

## 4. Verdict function (exact)
Inputs: (k1, n1) and (k2, n2). n is the number of usable runs. k is the number
of usable runs with the target outcome (for example "violating attempt").
Constants: MIN_RUNS = 5. z = 1.96.
- Wilson interval for (k, n): low and high.
- Difference interval for the pair: Newcombe hybrid over the two Wilson intervals.
Verdict values: InconclusiveSmallN, FirstHigher, FirstLower, Inconclusive.
Rule:
1. if min(n1, n2) < MIN_RUNS then InconclusiveSmallN
2. else let (lo, hi) = difference interval of (k1/n1) minus (k2/n2)
   - lo > 0 gives FirstHigher
   - hi < 0 gives FirstLower
   - otherwise Inconclusive

Properties:
- V1 Totality and exclusivity: exactly one verdict value for any valid input.
- V2 Small-n rule: if min(n1, n2) < MIN_RUNS the verdict is InconclusiveSmallN,
  whatever k1 and k2 are.
- V3 Swap symmetry: verdict(a, b) = flip(verdict(b, a)). flip swaps FirstHigher
  and FirstLower and fixes the other two values.
- V4 Identical counts: verdict((k, n), (k, n)) is never FirstHigher or FirstLower.
- V5 Interval bounds: 0 <= low <= k/n <= high <= 1 for 0 <= k <= n, n >= 1.
- V6 Noise validity: if a pair is declared a noise pair (A and its repeat) and its
  verdict is FirstHigher or FirstLower, the report status is NoiseFloorTooHigh and
  no effect verdict that uses that noise arm is emitted.

## 5. Decision table (exact)
EffectResult: RuleLowersViolations, NoMeasurableEffect, RuleRaisesViolations,
NotEnoughRuns, Invalid.
- Invalid: the noise arm showed a difference (V6).
- NotEnoughRuns: the verdict was InconclusiveSmallN.
- RuleLowersViolations: leave-one-out arm higher than rule arm (FirstHigher).
- RuleRaisesViolations: leave-one-out arm lower than rule arm (FirstLower).
- NoMeasurableEffect: Inconclusive with enough runs. It says "not measurable at
  this n". It does not say "no effect".
Decision values: FixLoading, Keep, ReplaceWithGuard, DeleteCandidate,
NeedsMoreRuns, CannotDecide.
Inputs: reach in {Loaded, Masked, Unknown}; effect in EffectResult;
guard in {GuardMatchesRule, GuardWorse, GuardUntested}.
- D1 reach = Masked gives FixLoading (any effect, any guard).
- D2 reach = Unknown gives CannotDecide.
- D3 reach = Loaded and effect = Invalid gives CannotDecide.
- D4 reach = Loaded and effect = NotEnoughRuns gives NeedsMoreRuns.
- D5 reach = Loaded and effect = RuleRaisesViolations gives DeleteCandidate.
- D6 reach = Loaded and effect = NoMeasurableEffect gives DeleteCandidate.
- D7 reach = Loaded and effect = RuleLowersViolations and guard = GuardMatchesRule
  gives ReplaceWithGuard.
- D8 reach = Loaded and effect = RuleLowersViolations and guard in
  {GuardWorse, GuardUntested} gives Keep.
Derived properties:
- D9 Totality and determinism: the table is a total function on all inputs.
- D10 Safety: ReplaceWithGuard only when guard = GuardMatchesRule and
  effect = RuleLowersViolations and reach = Loaded.
- D11 Safety: DeleteCandidate is never returned when effect = RuleLowersViolations.
- D12 Masked rules are never reported as Keep, ReplaceWithGuard or DeleteCandidate.
GuardMatchesRule means: guard-only completion is not lower than rule-arm completion
by the verdict function (verdict is not FirstLower for guard-only against rule arm
on the "completed" outcome, with enough runs) and the guard blocked every
violating command it saw.

## 6. Run lifecycle (state machine)
Plan states: Drafted, WorldValidated, ReachabilityChecked, Running, Complete,
BudgetStopped, Aborted, Analyzed, Reported.
Order: Drafted, WorldValidated, ReachabilityChecked, Running, then Complete or
BudgetStopped, then Analyzed, then Reported. Aborted is reachable from any
non-final state.
Run states: Pending, Started, RecordedUsable, RecordedUnusable.
Safety:
- L1 No run is Started before the plan is Running, which needs WorldValidated and a
  ReachabilityChecked result (Loaded, Masked or Unknown) for every arm.
- L2 Budget: a run is Started only if spent + RUN_CAP <= BUDGET. So spent <= BUDGET.
- L3 Immutability: a recorded run never changes.
- L4 Idempotent resume: a cell never has more than `reps` runs. Resuming skips cells
  that are full.
- L5 No verdict before the plan is Complete or BudgetStopped.
- L6 Counts use usable runs only. Unusable runs are excluded from n and k.
- L7 An arm with reach = Unknown gets no effect verdict.
- L8 No effect verdict is Reported unless the plan has a noise pair.
Liveness (under a fair runner):
- T1 Every Started run is eventually Recorded (usable or unusable).
- T2 Every Running plan eventually reaches Complete or BudgetStopped.

## 8. Out of formal scope (be honest in every document)
- Agent behavior (LLM output) is not formalized. It is measured.
- Shell command parsing for violation checks is covered by property tests and a
  corpus of good and bad commands, not by proofs.
- The numeric Wilson and Newcombe implementation is covered by property tests and
  known-value tests. Lean treats interval endpoints as an oracle with the V5
  axiom and the swap axiom.
- The `claude` CLI, hooks and permission behavior are observed, not proven.
- TLA+ models are bounded. Passing a bounded run is not a proof for all sizes.

## 9. Checkpoint rule
A milestone is done only when its executable gates pass: tests green, checks
proven able to fail (a bad example each check must reject), the TLC runs agree
with their expected verdicts, the Lean project builds with no `sorry`, and the
spend stays under the stated cap.
